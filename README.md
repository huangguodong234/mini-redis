# mini-redis

纯 C 手写的内存键值存储引擎：**RESP 协议编码 + 8 个命令 + epoll 事件循环 + 定时器**。
从 socket、协议解析到哈希表、跳表、SDS，全部手写，**零第三方依赖**。

```mermaid
flowchart LR
    A["客户端<br/>redis-cli / nc / 自研压测"] -->|"TCP + RESP"| B["mini-redis<br/>单线程事件循环"]
    B -->|"SET / GET / ZADD ..."| C["内存存储<br/>哈希表 + 跳表"]
```

| | |
|---|---|
| **语言 / 依赖** | C99 · 无第三方库 · Linux（epoll） |
| **网络模型** | 单线程 epoll 事件循环 + 非阻塞 IO + 输出缓冲 |
| **协议** | RESP（数组协议）+ inline 命令（兼容 nc/curl） |
| **命令** | `PING` `SET` `GET` `DEL` `ZADD` `ZREM` `ZSCORE` `ZRANGE` |
| **代码量** | `src/` 3936 行 · `include/` 1384 行 |
| **验证** | 集成 54/54 · 单元 6/6 · ASan/UBSan/LSan 零泄漏 · 零告警 |

> ⚠️ **定位：学习与能力验证项目，不是生产可用服务。**
> 缺认证、内存上限、持久化；有序集合是**全局单例**（`ZADD` 的 key 被忽略）。
> 详见 [§7 与 Redis 的差距](#7-与-redis-的差距)。

## 1. 快速开始

### 编译与运行

```bash
make                      # 生成 mini-redis
./mini-redis              # 默认监听 0.0.0.0:6379
./mini-redis 6380         # 指定端口（优先级：命令行 > PORT 环境变量 > 6379）
```

| 环境变量 | 默认 | 作用 |
|---|---|---|
| `PORT` | 6379 | 监听端口（命令行参数优先级更高） |
| `CLIENT_TIMEOUT` | 0（不超时） | 客户端空闲多少秒后被断开 |

```mermaid

```

```mermaid
flowchart LR
    Y1["epoll_wait 报<br/>fd 可读"] --> Y2["readQueryFromClient"] --> Y3["processInputBuffer<br/>解析 + 执行"] --> Y4["handle_command"] --> Y5["send_* 写进 outbuf<br/>【只入队】"]
    Y5 -.->|"下一轮 beforesleep"| Y6["writeToClientRaw<br/>【真正 write】"]
```

```mermaid
flowchart LR
    Z1["协议错误 / 对端关闭<br/>写错误 / 空闲超时"] --> Z2["freeClient"] --> Z3["⓪ flush outbuf"] --> Z4["① DEL READABLE<br/>+ WRITABLE"] --> Z5["② close(fd)"] --> Z6["③ clients_remove"] --> Z7["④ 释放内存"]
```

> ★ **链路 2 是理解本项目的关键**：`send_*` 只把数据**追加进 outbuf 就返回**，
> 真正 `write` 发生在**下一轮循环的 `beforesleep`**。
> 这是「非阻塞 + 输出缓冲」与「阻塞直发」最本质的区别 ——
> 好处是攒批（一条 `+OK` 从 3 次 `write` 降到 1 次）且永不阻塞，
> 代价是「数据已就绪但未发出」这个状态要由我们自己维护。

## 4. 请求生命周期

以一条 `SET name mini-redis` 为例：

```mermaid
sequenceDiagram
    participant C as 客户端
    participant K as 内核
    participant AE as ae.c
    participant NET as networking.c
    participant P as parser.c
    participant CMD as commands.c
    participant R as reply.c
    participant S as storage.c

    C->>K: *3\r\n$3\r\nSET\r\n...
    K->>AE: epoll_wait 返回（fd 可读）
    AE->>NET: rfileProc = readQueryFromClient
    NET->>K: read(fd, buf, 4096)
    K-->>NET: 26 字节
    NET->>NET: 更新 c->lastinteraction
    NET->>NET: 追加进 c->querybuf
    NET->>P: processInputBuffer(c, store, zset)
    P->>P: 状态机解析出 argv = [SET, name, mini-redis]
    P->>CMD: handle_command(c, cmd, store, zset)
    CMD->>S: storage_set("name", "mini-redis")
    S-->>CMD: OK
    CMD->>R: send_simple_string(c, "OK")
    R->>R: sdscatlen(c->outbuf, "+OK\r\n")
    Note over R: 到此为止，一个字节都没发出去
    R-->>P: 返回
    P-->>NET: 返回
    NET-->>AE: 返回
    Note over AE: 本轮结束，进入下一轮
    AE->>NET: beforesleep → beforeSleep(el)
    NET->>K: writeToClientRaw → write(fd, "+OK\r\n")
    K->>C: +OK\r\n
```

### 四个常被问到的细节

| 问题 | 答案 |
|---|---|
| 为什么 `send_*` 不直接 `write`？ | 非阻塞 `write` 遇 `EAGAIN` 只能发出去一部分；剩余数据不存起来就是**发送半包**。 |
| 一次 `read` 只读 4096 字节，大命令怎么办？ | epoll 用**水平触发（LT）**：没读完内核会继续通知，回调会再次被调。 |
| 客户端发一半（半包）会怎样？ | 状态机把进度存在 `c->qb_pos` / `multibulklen` / `bulklen` 里，下次从断点续解。 |
| 一个客户端发很多命令会占满 CPU 吗？ | 会 —— `processInputBuffer` 的 `while` 循环**没有限流**，属已知局限（Redis 有限制）。 |

### 5.3 混合负载测试（真实生产环境模拟）

```bash
make mixtest         # 15s 预热 + 45s 主压，约 60 秒
make mixtestquick    # 缩短规模冒烟，约 20 秒
```

`prod_test.py` 是**体检**：每组用受控的单一负载对标一个明确的问题。
`mixload.py` 是**演练**：把七类流量**同时**压上去，只回答一件事——
**混在一起还活不活？**

| 流量源 | 模拟什么 |
|---|---|
| 正常业务 | 9 种命令按真实权重混合 + 随机流水线深度 1~32 |
| 连接潮汐 | 连接数按正弦起伏（峰谷比可配，默认 30:1） |
| 只连不发 | 负载均衡探活、被防火墙墙住的半开连接 |
| 恶意流量 | 11 种非法请求（非法首字节 / 参数超限 / 长度不兑现…） |
| 请求缓冲膨胀 | 只发合法开头、永不成包（每字节都合法） |
| 只发不收 | 下游卡死：发命令但永不读回复 |
| 慢速攻击 | 一次 1 字节，把单条命令拖很长 |

**13 项判定**，其中一条专门防「测试自己失效」——若某类流量一条请求都
没发出去（比如线程静默异常退出），该项直接判失败。
> 这条是踩出来的：早期版本里预算变量写错类型，4 个业务线程全部静默退出，
> 测试照常打印「8/9 通过」——**一张满分成绩单，测的是空气**。

实测结果见 [§6.7 混合负载](#67-混合负载七类流量同时压上来)。

## 6. 性能数据

**环境**：12 核 · 15.9 GB · WSL2 · 内核 6.18.40.1 · 每点 3 次取中位数
**客户端**：`bench/loadgen.c`（C 多进程，无 GIL 限制）

> ⚠️ **为什么必须用 C 客户端**：Python 多线程受 GIL 限制，并发 ≥4 时
> **客户端自己**成为瓶颈，曲线失真（实测症状：并发 2 比并发 4 还快）。
> ★ 测量工具不能成为瓶颈，否则测的是工具而不是被测对象。

### 6.0 先读这里：六组数字量的是不同的东西

直接比大小会看着矛盾（8,374 vs 818,633 vs 1,840,000 vs 18,042），
因为它们**测的不是同一件事**：

| 小节 | 测什么 | 单位 | 瓶颈在 |
|---|---|---|---|
| 6.1 | 1 条连接，调「连发多少条」 | 命令/秒 | depth 小→延迟；depth 大→单核 CPU |
| 6.2 | N 条连接，depth 固定 100 | 命令/秒 | 2~4 连接后→单核 CPU |
| 6.3 | 1 条连接，发一条等一条 | 微秒/次 | 网络往返，**不是**服务器算力 |
| 6.4 | 写 320 KB 的大 value | 字节/秒 | 内存带宽 |
| 6.5 | 阻塞版 vs epoll 版 | 倍率 | —— |
| **6.7** | **七类流量混在一起** | **命令/秒** | **真实线上的综合表现** |

> ★ 一句话：**6.1 问「单核最快能多快」，6.2 问「几条连接能喂饱它」，
> 6.3 问「用户感受到多快」，6.5 问「为什么必须换」，
> 6.7 问「真上线了能扛住多少」。**
>
> ⚠️ **6.1~6.6 都是受控的单变量实验**（一次只改一个东西）；
> **6.7 是混合负载**（所有情况同时来）。前者用来定位瓶颈，后者用来报容量。

### 6.1 单连接：流水线深度的作用

调「一次连发多少条再统一收回复」，把 TCP 往返的等待时间用起来：

| depth | QPS | 单条耗时 | 相比上一档 |
|---|---|---|---|
| 1 | 8,374 | 119.4 µs | — |
| 10 | 78,720 | 12.7 µs | 9.4× |
| 100 | 703,733 | 1.42 µs | 8.9× |
| 500 | **1,840,000** | 0.54 µs | **2.6×** ← 收益递减 |
| （上一轮参考） | 2,506,833 | 0.40 µs | —— |

> ★ **depth=1 的 119.4 µs 与 6.3 的 p50（90.4 µs）同一个量级** —— 互相印证
> （depth=1 每次都要重新建一轮往返，比复用连接的串行 RTT 略高，符合预期）。
> depth=1 时服务器只干了约 1 µs 的活，其余 98% 都在等网络，CPU 闲着。
> 加大 depth 就是填满这段等待，到 depth=500 时等待已可忽略 →
> **184 万（本轮）/ 250 万（上轮）就是这颗单核的算力上限。**
>
> ★ **收益递减点很关键**：100→500 只涨 2.6 倍（depth 涨 5 倍）。
> 说明 depth=100 时瓶颈已从「延迟」变成「算力」—— 这正是 6.2 选 depth=100 的依据。
>
> ★ **绝对值会随机器状态漂移**：同一份代码在负载更轻的时候测到深度 500 是
> **250 万 QPS**。表中采用**偏保守**的一组（184 万），并保留上一轮数字做对照——
> 想说明的是**曲线形状**（9.4× / 8.9× / 2.6×）比绝对峰值稳定得多。

### 6.2 多连接：要几条才能喂饱单核

depth 固定 **100**（依据见 6.1），只增加连接数：

| 并发 | QPS | 相对 1 连接 | 增涨 |
|---|---|---|---|
| 1 | 818,633 | 1.00× | — |
| 2 | 1,244,333 | 1.52× | **+36 点（利用率）** |
| 4 | 1,468,433 | 1.79× | +7 点 |
| 8 | 1,413,600 | 1.73× | −0.4 点 |
| 16 | 1,354,866 | 1.65× | —— |

**结论：4 条连接就够了，之后加多少都不涨。** 机制（用
`/proc/<pid>/stat` 的 CPU 记账 + `/proc/<pid>/status` 的上下文切换数实测）：

| 并发 | CPU 利用率 | `epoll_wait` 每秒调用 |
|---|---|---|
| 1 | 54.3% | **7,998 次** |
| 2 | 89.9% | 11,350 次 |
| 4 | **96.6%** | 5,416 次 |
| 8 | 96.2% | **2,189 次** |
| 16 | 96.5% | —— |

```mermaid
flowchart LR
    A["单连接：处理完一批就进 epoll_wait<br/>而数据还在 TCP 往返中"] --> B["★ 睡下，CPU 闲置 45%"]
    C["多条连接：往返互相错开<br/>A 在处理时 B 的数据已就绪"] --> D["★ epoll_wait 总能立刻返回<br/>睡眠消失，利用率补满"]
```

> ★ **为什么是 4 而不是 2**：那 46% 的空洞不是均匀补上的 ——
> 1→2 补掉大头（+36 点），2→4 补掉零头（+7 点），4 之后不再涨。
> **「4」是边际收益跌破噪声的经验位置，不是公式算出的临界点。**
>
> ★ **`epoll_wait` 那两列要这么读**：它不是「越多越好」也不是「越少越好」。
> 并发 1 时睡眠多（7998 次/秒）= CPU 闲着等数据；并发 8 时降到 2189 次/秒 =
> 事件总是排着队，睡不下去，**这才是「喂饱了」的形状**。
> 中间 2→4 那次的 11,350 是一次抖动（该轮 CPU 已 90% 以上，采样窗口里
> 恰好撞上几次长等待），趋势看两端即可。
>
> ★ **封顶 95% 而非 100%**：每轮都要重新进 `epoll_wait`，加上调度与内存拷贝。
> （深挖这个成本的实验记录见 §6.6）
>
> ★ **命令越重，这个数越小**：命令重 → 单连接利用率高 → 离饱和更近。

| value 大小 | 单连接利用率 | 1→2 连接涨幅 | 饱和点 |
|---|---|---|---|
| 14 B（PING） | 60.9% | 1.69× | **2 条** |
| 320 KB | **95.0%** | 1.07× | **1 条** |
| 1 MB | **94.8%** | 0.96× | **1 条** |
| 8 MB | **94.9%** | 1.25× | **1 条** |

> ★ **判据说明**：表中「饱和」= 该并发下单连接 CPU 利用率已达 **95% 左右**，
> 再加连接只分摊、不增产。本轮用 `/tmp` 下的定点客户端对每个 (value, 并发) 组合
> 各测 3 次取中位，都是**新建服务器进程**测的，避免前一轮的状态污染。
>
> ★ **趋势比上一轮更陡**：命令重 2 万倍（14 B → 320 KB），饱和点就从 2 掉到 1。
> 原因是数据量一大，单条命令的**内存搬运**本身就足够喂满一颗核 ——
> 这也解释了为什么 §6.4 大值吞吐只有几百 MB/s 而不可能更高。
>
> ⚠️ **8 MB 那行精度最差**：1 秒内只能完成一百多次，QPS 抖动大，
> 「1 条」的结论可靠（利用率已达 95%），但小数值差异无意义。
>
> ⚠️ 所以「2~4」是**「需要多少并发才能喂满单核」的量级**，
> 不是「这台机器只能接 2 条连接」。表格上方的 6.2 主表用的是 depth=100 的
> PING 流量，那里是 4；这里按 value 加重到 320 KB 以上就降到 1。
> **两个数都对，量的东西不同。**

### 6.3 延迟（串行 RTT，N=3000）

发一条、等回复、再发下一条 —— 这是**用户能感知到的体感延迟**：

| 分位 | 延迟 |
|---|---|
| 平均 | 104.3 µs |
| p50 | **90.4 µs** |
| p90 | 146.6 µs |
| p99 | **202.4 µs** |

> ★ 数值为 **5 轮 × 3000 样本取中位**（每轮独立新建服务器进程）。
> 单轮之间 p50 在 88~102 µs 波动，是 WSL2 调度噪声，不是服务端抖动。
>
> ★ p99 / p50 = **2.2×**，长尾不严重。
>
> ★ 这 90.4 µs 里服务器只占极小部分：按 6.1 的 depth=500（单条 0.54 µs）算只有 **0.6%**；
> 即使按 6.2 的饱和值（单条约 1.2 µs）算也只有 **约 1.3%**，其余全是往返与调度。
> **要看服务器算力看 6.1，要看用户体验看 6.3。**

### 6.5 A/B：为什么必须换 epoll

`bench/setup_ab.sh` 把阶段 1 的阻塞版从 git 历史 `c49f44c` 导出并现场编译到
`/tmp/ab/blocking`，当前代码编到 `/tmp/ab/epoll`。**是真的两套可执行文件交替运行，
不是模拟阻塞。**

四个子测试逐层递进：**① ② 是「有没有」，③ 是「差多少」，④ 是「输在哪」。**

**① 静默客户端能否卡死服务器**（连接 A 不发数据，看连接 B 能否被服务）

| | 第 2 条连接能否服务 | 耗时 |
|---|---|---|
| 阻塞版 | ❌ **否** | 2004 ms（超时） |
| epoll 版 | ✅ 是 | 1 ms |

> 阻塞版 `accept` 后陷进那个连接的 `read`，对方不发数据就永久阻塞 → **整个服务器停摆**。

**② 10 条并发连接中被服务的条数**（3 次取最好）

| | 被服务 |
|---|---|
| 阻塞版 | **1/10** |
| epoll 版 | **10/10** |

> 取最好的一次上报 —— 这是对阻塞版最有利的取值，即便如此也只有 1/10。

**③ 吞吐**

| 场景 | 阻塞版 | epoll 版 | 倍率 |
|---|---|---|---|
| 并发 1 · depth=100 | 39,366 | **824,600** | **20.9×** |
| 并发 4 · depth=100 | 39,166 | **1,418,066** | **36.2×** |

> 阻塞版**并发 4 比并发 1 还略低** —— 它的吞吐全部来自「单连接流水线」，加连接毫无收益。
> ★ 别读成「阻塞版很慢」：它单连接也能跑约 4 万 QPS，真正的问题在 ④。

**④ 公平性 —— 这才是「瓶颈」的准确画像**

8 条连接各跑 2 秒，看**每条各自完成了多少请求**（读分布形状，不读绝对值）：

| | 各连接完成数（降序） | 被公平服务 | 离散度 CV |
|---|---|---|---|
| 阻塞版 | `[100400, 100, 100, 100, 100, 100, 100, 100]` | **1/8** | **2.62** |
| epoll 版 | `[102100, 101300, 100400, 100100, 98000, 97800, 96600, 96200]` | **8/8** | **0.02** |

> ★ **离散度相差约 130 倍**，比总 QPS 锋利得多。
> 阻塞版的模式：**1 条连接跑满 10 万次，另外 7 条各完成 100 次后彻底卡死**
> （那 100 次是建连后第一批来得及发出去的）。
>
> **为什么总 QPS 会掩盖它**：那条幸运连接把总吞吐撑到 5 万，看着「只是慢十几倍」，
> 真相是**它一次只能服务一个人**。
>
> ⚠️ 这里用 Python 多线程（受 GIL 限制），所以**只能读分布形状，不能读绝对值**。

**结论**

| 阻塞版的瓶颈 | 表现 |
|---|---|
| 不是「慢」 | 单连接吞吐其实可观（约 5 万 QPS） |
| 而是「一次只能服务一个连接」 | 8 条并发里只有 1 条在跑 |
| 更糟的是「会被一个客户端卡死」 | 一条不发言的连接让服务完全不可用 |

> ★ 本项目这类服务的本质是「同时等很多个连接，但每个连接大部分时间没事干」。
> 阻塞式 `accept` + `read` **在结构上无法表达「同时等多个」** ——
> 不是慢几倍，而是这个能力根本不存在。

### 6.6 深挖：write 到底花多少时间

「4 条连接封顶 95%」引出一个问题：**那 5% 是什么？**
用独立工具 `bench/bench_syscall.c`（不经过 mini-redis）测出环境基线：

| 测量项 | 中位数（40 万次） |
|---|---|
| `write` 5 字节 → loopback | **6,008 ns** |
| `write` 50 / 500 / 4096 字节 | 5,283 / 6,112 / 6,004 ns |
| `read` 64 字节 | 1,457 ns |
| `epoll_wait` 超时=0 | 829 ns |
| `getpid`（syscall 地板价） | 726 ns |

> ★ **write 的耗时与数据量无关**（5 字节 vs 4096 字节几乎一样）——
> 说明是**每次调用的固定成本**，不是拷贝成本。
> 本轮每个采样点从 20 万次提到 **40 万次**，中位数更稳；
> 数值整体比上一轮高约 10%（4.5~6.0 µs 区间流动），属同一量级的环境波动。
> 5.3 µs 偏高（原生 Linux 通常 1~3 µs），是 **WSL2 要穿越 Hyper-V 边界**的代价。

**服务器实测与基线对比**：

| 场景 | 单次 write | 相对基线 |
|---|---|---|
| 环境基线（裸程序） | **6,008 ns** | 1.0× |
| 服务器·客户端读得慢 | 6,130 ns | **1.02×** |
| 服务器·客户端全速读 | 15,020 ns | 2.5× |
| 服务器·高并发压测 | 38,451 ns | 6.4× |

> ★ 后三行是按本轮新基线（6,008 ns）**等比例换算**的：原来的
> 5,285 / 13,248 / 33,693 与本轮的 6,008 都来自同一台机器同一工具，
> **倍率（1.02× / 2.5× / 6.4×）是稳的，绝对值随环境漂移。**
> 保留倍率、更新基线，比保留一组对不上的绝对值更有意义。

**为什么会有差异——不是数据量，是「调用上下文」：**

| write 前的工作量 | ① 冷 write | ② 紧接着的 write | 冷/热 |
|---|---|---|---|
| 无 | 4,066 ns | 4,067 ns | 1.00× |
| 空转 2000 次 | 5,185 ns | 3,355 ns | 1.55× |
| 空转 20000 次 | 21,860 ns | 6,507 ns | **3.36×** |

> ★ **同一个 write，前后紧挨着做两次，差 3.4 倍。**
> 多出来的 15.4 µs 不是处理数据，而是**让 write 看到它需要的内核状态**；
> 第二次不用重做所以便宜。空转 0 时冷热一致 —— 没有前置工作就没有这个代价。
>
> ★ 服务器每轮的 write 都是**冷的**（前面刚做完 epoll_wait → read → 解析 → 执行），
> 而基线程序紧循环只做 write，环境一直是热的。
> **这才是 95% 封顶的真正来源**，也是并发越高 write 越慢的原因
> （每轮干的事越多，把 write 的状态冲得越冷）。
>


### 6.7 混合负载：七类流量同时压上来

前面 6.1~6.6 都是**受控的单变量实验**——一次只调一个参数，回答一个明确的问题。
但真实线上跑的不是单一流量。这一节把所有情况**同时**压上去，只回答一件事：
**混在一起还活不活？活成什么样？**

```bash
make mixtestquick     # 约 20 秒冒烟
make mixtest          # 15s 预热 + 45s 主压
```

**环境**：同 §6 头部（12 核 · WSL2）· 90 秒主压 · 七类流量并发

| # | 流量源 | 模拟什么 | 实测活动（90s） |
|---|---|---|---|
| 1 | **正常业务** | 9 种命令按真实权重混合（读多写少、ZSET 占少数）+ 随机流水线深度 1~32 | **1,610,207** 次 · **0 错误** |
| 2 | **连接潮汐** | 连接数按正弦起伏，峰谷比 30:1 | 峰 59 连接 · 10,535 次探活 |
| 3 | **只连不发** | 负载均衡探活、被防火墙墙住的半开连接 | 376 条被超时清理 |
| 4 | **恶意流量** | 11 种非法请求：非法首字节 / 参数超限 / 长度不兑现 / 畸形 bulk | 299 次全部被隔离 |
| 5 | **请求缓冲膨胀** | 只发合法开头、永不成包（每字节都合法） | 7,262 次被 `MAX_QUERYBUF` 挡住 |
| 6 | **只发不收** | 下游卡死：发命令但永不读回复 | 140 条被输出缓冲上限断开 |
| 7 | **慢速攻击** | 一次 1 字节，拖长单条命令 | 202 次被超时清理 |

**结果**：

| 指标 | 数值 |
|---|---|
| 吞吐 | **18,042 QPS**（业务命令，含 ZSET 与 32KB 大值） |
| 业务延迟 | p50 **1.16 ms** · p90 2.92 ms · p99 **5.37 ms** · max 11.3 ms |
| 独立探针可用性 | **1,178 次 0 失败**（新建连接 PING，20 次/秒） |
| 内存 | RSS 峰值 **138 MB**，后半段相对前半段 **−0.5%**（无泄漏） |
| fd | 峰值 **48**（`MAX_CLIENTS` 上限 10000） |
| 服务端 CPU | 均值 **33.4%** |
| 崩溃 / 数据错误 | **0 / 0** |

> ★ **和 6.1 的 184 万 QPS 不矛盾**：这里测的不是「单核极限」，
> 而是「有一半 CPU 时间花在应付恶意连接、空连接、卡死连接时，还能交付多少有效吞吐」。
> **18,042 QPS 是这张成绩单里最该看的数**——它才是「业务真实能拿到多少」。

**连接潮汐：峰值 vs 谷值**

| 潮汐峰值 | QPS | 业务 p99 | 峰值段 CPU | 谷值段 CPU | RSS 峰值 |
|---|---|---|---|---|---|
| 60 连接 | 18,042 | 5.37 ms | 31.6% | 32.1% | 138 MB |
| **400 连接** | 15,808 | 14.4 ms | 35.0% | 31.4% | 129 MB |

> ★ **连接数涨 6.7 倍，CPU 几乎不动（31.6% → 35.0%）**——
> 这正是 epoll 该有的形状：**连接数是「挂着」的成本，不是「循环着」的成本**。
> 400 个空闲连接不产生任何 CPU 开销，只有真正发数据的才被处理。
>
> ★ **p99 从 5.4 ms 涨到 14.4 ms** 的原因不在服务端：400 条连接同时上线时，
> 连 Python 探针**自己**建连的排队时间（探针中位基线）就从 10 ms 涨到 64 ms。
> 服务端处理仍然是个位数毫秒。

#### 这一节挖出的真实缺陷

**★ 输出缓冲没有上限 —— 3 条连接就能把进程撑到 5.3 GB。**

| | 修复前 | 修复后 |
|---|---|---|
| 3 条「只发不收」连接跑 12 秒 | RSS **1 MB → 5,324 MB**（仍在涨） | RSS **稳定在 3 MB** |
| 业务 p99（同时有 nosink 流量） | **577 ms** | **5.4 ms** |
| 结果 | 拖向 OOM，整机不可用 | 超限应答 `-ERR output buffer limit reached` 后断开 |

- **根因**：对端不读 → `write()` 永远 `EAGAIN` → 回复全堆进 `c->outbuf`，
  而代码里**没有任何上限检查**（Redis 有 `client-output-buffer-limit`，本项目没有）。
- **修法**：在 `send_response` 入队处检查「未发送字节数」，超 `MAX_OUTBUF`（64 MB）
  打标记；由 `beforeSleep` 在「本轮所有回调都已返回」的安全点统一 `freeClient`。
  不在 `send_response` 里直接断开——那样会把调用栈上还在用的 `Client*` 变成悬垂指针。
- **顺带修掉一个 O(n²)**：`writeToClientRaw` 原先每写一块就把剩余几十 MB 整体
  `memmove` 到缓冲区头部。实测 64 MB 缓冲、每次写 4 KB 时**单次 memmove 要 6.4 ms**，
  累计 12.7 秒。改成发写游标 `outbuf_pos` 后，只在**全部发完**时回收一次空间。

> ★ **诚实记录一次误判**：测试过程中我一度认为解析器有「大包 + 流水线误杀」的 bug，
> 写了 100 行存档逻辑改 `parser.c`。回头用**原始 HEAD 构建**验证，
> 原代码在 8/8 种合法切分场景下完全正确——**那个 bug 不存在**，改动已全部回退。
> 留下的只有这条**如实记录**的协议边界：客户端声明 `$100` 却只发 0 字节值，
> 服务器会继续等那 100 字节（协议上说得通，是客户端没发够），不粉饰成 bug。

### 6.8 一页汇总

| 维度 | 结果 | 来自 | 回答什么问题 |
|---|---|---|---|
| 单连接峰值 | **1,840,000 QPS** | 6.1 | 这颗单核最快能多快 |
| 喂饱单核所需连接数 | **约 2~4 条** | 6.2 | 几条连接能用满 CPU |
| 并发峰值 | **约 1,470,000 QPS** | 6.2 | 加连接能否继续堆 |
| 串行延迟 | p50 **90.4 µs** · p99 **202.4 µs** | 6.3 | 单条命令的体感延迟 |
| 大值吞吐 | **686 MB/s** | 6.4 | 大数据搬运会不会塌方 |
| epoll vs 阻塞（吞吐） | **20.9× ~ 36.2×** | 6.5③ | 差距有多大 |
| epoll vs 阻塞（并发能力） | **1/10 → 10/10** | 6.5② | 并发能力有没有 |
| epoll vs 阻塞（公平性 CV） | **2.62 → 0.02** | 6.5④ | 到底输在哪 |
| **混合负载有效吞吐** | **18,042 QPS**（p99 5.37 ms） | 6.7 | 真实业务能拿到多少 |

> ★ **读法**：6.1~6.4 那四行是「epoll 版有多快」，
> 6.5 那三行是「为什么必须换」，最后一行是「真上线能扛多少」——
> **报容量报最后一行，别报单连接峰值。**
>
> ★ **几个数看着矛盾但都对**：
> · 184 万（6.1）与 147 万（6.2）是**同一颗单核的两种测法** ——
>   一个从「单连接压到最深」逼近，一个从「多连接堆到最满」逼近；
>   6.2 略低只是因为 depth 停在 100。
> · 90.4 µs（6.3）与 184 万 QPS 也不矛盾 ——
>   前者是发一条等一条的体感延迟，后者是流水线灌满后的极限。
> · 「2~4 条」是**需要多少并发才能喂满单核**的量级，**不是机器的连接数上限**。
> · **18,042 QPS（6.7）远低于 147 万**，因为它是**七类流量混在一起**的真实值：
>   一半 CPU 花在应付恶意/空闲/卡死连接上，而且命令里含 ZSET 与 32 KB 大值，
>   不是清一色的 PING。**要报「这台服务的容量」就报这个数。**
>
> ★ **所有绝对值都是这台 WSL2 机器的**。同一份代码在不同负载窗口下，
> 单连接峰值测到过 184 万和 250 万两组（差 36%）。
> **可信的是曲线形状与倍率，不是某个绝对数字。**

## 7. 与 Redis 的差距

准确说法是「**实现了 RESP 编码 + 8 个命令的子集**」。

### 7.1 命令语义差距

| 命令 | 本项目 | 真实 Redis | 影响 |
|---|---|---|---|
| `ZADD` | `key` 被忽略，**所有有序集合共享全局单例** | 按 key 隔离 | **高**：`ZADD a 1 x` 后再 `ZADD b 2 y`，`ZRANGE a 0 -1` 会同时看到 x 和 y |
| `ZADD` | 恒回 `+OK` | `:1`（新增）/ `:0`（更新） | 中 |
| `ZADD` | 不支持 `NX/XX/GT/LT/CH/INCR` | 支持 | 中 |
| `ZRANGE` | 不支持 `WITHSCORES/REV/BYSCORE` | 支持 | 中 |
| `PING` | 恒回 `+PONG` | `PING msg` 回 bulk | 中 |
| `SET` | 不支持 `EX/PX/NX/XX/GET` | 支持 | 低 |
| `DEL` | 只支持单 key | 支持多 key | 低 |
| `*0\r\n` | 视作协议错误并**断开连接** | 视作空命令 | 低 |

> 注：`test.sh` 中「12-arg PING (B3)」用例期望 `PONG`，
> 是把上述不兼容行为固化成了期望值。若日后对齐 Redis，该用例需一并修改。

### 7.2 服务能力差距

| 能力 | 本项目 | Redis |
|---|---|---|
| 网络模型 | 单线程 epoll | 单线程 epoll + 多 IO 线程 |
| 认证 | ❌ 无 | ACL / requirepass |
| 内存上限 | ❌ 无 | maxmemory + 淘汰策略 |
| 持久化 | ❌ 无 | RDB / AOF |
| 数据库分库 | ❌ 单库 | 16 个 db |
| 单次命令数限流 | ❌ 无 | 有 |
| 客户端空闲超时 | ✅ 有（轮询，需 `CLIENT_TIMEOUT` 开启） | 有 |
| 连接数超限的拒绝方式 | ✅ 先回 `-ERR max number of clients reached` 再关 | 有 |
| 请求缓冲超限的拒绝方式 | ✅ 先回 `-ERR query buffer limit reached` 再关 | 有 |
| fd 耗尽的拒绝方式 | ✅ 先回 `-ERR out of file descriptors (EMFILE/ENFILE)` 再关（预留应急 fd） | 有（同样预留应急 fd） |

## 9. 开发日志

### 阶段 1-4：从阻塞到 epoll 事件循环

| 阶段 | 内容 | 关键产出 |
|---|---|---|
| **1** | `ae.h` / `ae.c` / `ae_epoll.c` 事件循环骨架 | 空跑验证 ae 层正确性 |
| **2** | 接入事件循环，新建 `networking.c` | 可同时服务多连接（阶段 0 做不到） |
| **3** | 输出缓冲 `outbuf` + 非阻塞发送 | 慢客户端不再拖累他人 |
| **4** | 时间事件（定时器）+ `serverCron` 轮询式空闲超时 | `epoll_wait` 不再无限睡眠 |

**阶段 3 的核心变化**：

| | 改造前 | 改造后 |
|---|---|---|
| `send_response` | `while` 循环 `write`，阻塞到发完 | `sdscatlen` 进 `outbuf`，立即返回 |
| 「还没发出去」的状态 | 由**内核**发送缓冲区暗中承担 | 由**我们自己的** `outbuf` 显式持有 |
| 一条 `+OK` 的系统调用 | 3 次 `write` | 1 次 `write` |
| 对端读得慢时 | 整个服务器停摆 | 只影响该连接 |

**阶段 4 的两个设计决定**：

- 定时器用**无序双向链表 + O(n) 扫描**（同 Redis）——
  前提是**定时器数量不随连接数增长**，本项目只有 `serverCron` 一个。
- 客户端空闲超时用**轮询**而不是「每连接一个定时器」——
  后者在 10000 连接时会产生 10000 个定时器节点，
  而 `aeSearchNearestTimer` / `processTimeEvents` **每轮都要跑**。

### 阶段 5：解耦（`server.c` 一分为四）

原 `server.c` 526 行里挤了三种「变化原因完全不同」的职责：

| 文件 | 职责 | 变化原因 |
|---|---|---|
| `parser.c` | 三层解析器 | 协议规则变了 |
| `reply.c` | 响应编码 | RESP 输出格式变了 |
| `networking.c` | 网络驱动 | 网络模型变了 |
| `server.c` | socket + 连接生命周期 | fd 资源管理 |

同时斩断的隐式依赖：

- `freeClient(c)` → `freeClient(el, c)`：撤关注要的 `el`，所有调用点手头就有
- `writeToClientRaw` / `beforeSleep` 不再读 `g_server.el`
- **删除 `Server.el` 字段** —— 改完后它变成「只写不读」的死状态
- `BACKLOG` / `set_nonblocking` 三份定义 → `include/util.h` 一份

### 阶段 6：渐进式 rehash

先写 `bench/bench_rehash.c` **量化出瓶颈**：一次性搬迁在 100 万键时造成 **23.87 ms** 停顿，
且随 N 线性增长（10 万 3.71 ms / 200 万 57.99 ms）—— 证明问题真实存在，不是背结论。

实现渐进式 rehash 后：最大停顿从 **58 ms → 亚毫秒**（约 78×~120×），
且不再随 N 量级跃升 —— 这正是 O(n)→O(1) 的签名。

### 阶段 7：混合负载测试与收尾

前六个阶段都在回答「怎么把它做出来」。阶段 7 回答另一个问题：
**做出来的东西，真上线了会怎样？**

分两步走：

| 步骤 | 做法 | 产出 |
|---|---|---|
| **① 造场景** | 写 `bench/mixload.py`，把七类真实流量同时压上来 | 13 项自动判定 |
| **② 按结果收尾** | 把测试挖出的缺陷一条条补掉，并统一错误路径 | 见下表 |

**这一步发现了什么**（完整数据见 [§6.7](#67-混合负载七类流量同时压上来)）：

| 缺陷 | 严重度 | 状态 |
|---|---|---|
| `outbuf` 无上限：3 条连接 → RSS 5.3 GB → OOM | 🔴 致命 | ✅ 已修（`MAX_OUTBUF` + 延迟断开） |
| `writeToClientRaw` 的 O(n²) memmove | 🟡 中 | ✅ 已修（发送游标 `outbuf_pos`） |
| 7 条错误路径中 6 条只 `close()` 不回话 | 🟡 中 | ✅ 已修（见教训四的收尾表） |
| fd 耗尽时连错误都发不出（无 fd 可用） | 🟡 中 | ✅ 已修（预留应急 fd） |

**收尾阶段的核心认知**：

> 功能正确性靠**回归测试**保证，线上可运维性靠**错误路径**保证。
> 这两件事的验收方式完全不同 ——
> 前者问「做对了吗」，后者问「出问题时别人能不能看懂发生了什么」。

> ★ 一个只有"正常路径"做得漂亮的服务器，在故障现场提供的有效信息是零。
> 它会把每一次资源耗尽都伪装成「网络问题」。

### ★ 五个值得记的教训

#### 教训一：测量工具不能成为瓶颈

写生产测试时，用 Python 多线程压测得到一条荒谬的曲线：
**并发 2 比并发 4 还快**。

查证后发现：Python 的 GIL 让多线程实际串行执行，
并发 ≥4 时**客户端自己**成了瓶颈。
改用 C 多进程客户端后曲线正常（1→2→4 递增，4 连接后饱和）。

> **当测量结果违背常识时，先怀疑测量本身。**

#### 教训二：拿局部性能数字否定还没理解的设计

调渐进式 rehash 时，我一度认为「路径 A 和路径 B 应该叠加执行」，
并写进文档说二选一是 bug。**连续三次都错了**：

| 轮次 | 结论 | 错在哪 |
|---|---|---|
| 1 | 「关掉路径 A 更快 → 路径 A 没用」 | 我的 A/B 副本把 `else` 写成「只查旧表」，测试本身错了 |
| 2 | 「叠加版更快 → Redis 的 `if/else` 是 bug」 | 叠加快是因为**总工作量更大**，不是效率更高 |
| 3 | 「用 `rehashidx` 判断查哪张表会漏查 8.6%」 | 规则漏写「跳过旧表后仍要查新表」，测的是我自己的 bug |

**真相**：Redis `unstable` 的 `_dictRehashStepIfNeeded` **就是 `if/else` 互斥的**，
我最初的写法与它**语义完全等价**。是我的「修复」偏离了上游。

> **共同错因：拿一个局部的性能数字，去否定一个我还没理解的设计。**
> **当测量结果与上游成熟实现冲突时，先假设自己错了。**

#### 教训三：分批游标不能持有对象地址

`serverCron` 的分批扫描最初用 `static Client *cursor` 记住「上次扫到哪个节点」。
那个节点可能在下一次 `serverCron` 之前被 `freeClient` 释放 → 游标成野指针。

ASan 抓到的现场：

```
ERROR: AddressSanitizer: heap-use-after-free
    #0 serverCron          src/networking.c:486
    #1 processTimeEvents   src/ae.c:339
  freed by: freeClient
```

**修复**：改用**时间分片** —— 只检查「空闲时长落在本片区间」的客户端，
轮转状态是一个整数（`cronloops % slices`），不持有任何对象地址。

> **教训：分批游标要存「可重算的标量」（下标/时间），不要存「对象地址」。**
> 地址的生命周期不受你控制。

#### 教训四：没有上限的地方就有天花板，只是它在别人手里

混合负载测试（§6.7）挖出的最严重缺陷：**`outbuf` 没有上限**。

一个连上来、拼命发命令但**从不读回复**的客户端，会让服务器把回复不断堆进
`c->outbuf`；而 `write()` 永远返回 `EAGAIN`（对端收窗口是满的），于是
**只增不减**。实测 3 条这样的连接：

| 时间 | RSS |
|---|---|
| 0 s | 1 MB |
| 1 s | 747 MB |
| 3 s | 1,949 MB |
| 6 s | 3,113 MB |
| 12 s | **5,324 MB（仍在涨）** |

一条连接就能把整台机器拖进 OOM。

**修复**：在 `send_response` **入队处**检查未发送字节数，超 `MAX_OUTBUF`（64 MB）
打标记，由 `beforeSleep` 统一 `freeClient`。

> **为什么不在 `send_response` 里直接断开**：它可能深藏在
> 「解析 → 执行命令 → 编码回复」的调用栈里，那一刻断开会把调用栈上
> 所有还在用的 `Client*` 变成悬垂指针。
> **「打标记 + 延迟到安全点处理」是事件循环里关闭连接的通用手法。**

> **教训：凡是「生产者速度不受消费者控制」的缓冲区，都必须在写入口设上限。**
> 这个上限不是性能优化，是**把决定生死的开关从对手手里拿回来**。

**后续补上的一条：上限之外，还要给出「为什么」。**

设了上限之后，超限时客户端收到的是什么？

| 路径 | 修复前 | 修复后 |
|---|---|---|
| 连接数超 `MAX_CLIENTS` | 裸 `close()` → 客户端只看到 `Connection reset by peer` | 先发 `-ERR max number of clients reached` 再关 |
| 请求缓冲超 `MAX_QUERYBUF` | 只打一行服务端日志就 `close()` | 先发 `-ERR query buffer limit reached` 再关 |

> 两者的差别不是「多一句话」，而是**排查成本差一个数量级**：
> 拿到 RST 的人只能猜是「服务器满了」「网络抖动」还是「自己协议写错了」；
> 拿到 `-ERR` 的人当场就知道该改什么。

> **教训：拒绝也要有理由。** 一个静默关闭的连接，对客户端来说等价于故障。

#### ★ 收尾：把所有「静默关闭」清一遍

上面那条教训不该只用在两处。收尾时我把 `networking.c` 里**每一条**
可能关闭连接的路径都过了一遍，统一成「能回话就一定要回话」：

| 触发条件 | 修复前客户端看到 | 修复后收到 | 为什么以前不告诉 |
|---|---|---|---|
| 连接数超 `MAX_CLIENTS` | `Connection reset by peer` | `-ERR max number of clients reached` | 裸 `close()` |
| 请求缓冲超 `MAX_QUERYBUF` | 同上 | `-ERR query buffer limit reached (client-query-buffer-limit)` | 只打服务端日志 |
| **fd 耗尽（EMFILE/ENFILE）** | **什么都没收到，干等超时** | `-ERR out of file descriptors (EMFILE)` | 见下方说明 |
| `create_client` 内存不足 | `Connection reset by peer` | `-ERR out of memory` | 裸 `close()` |
| 事件注册失败 | 连上了但永不回话 | `-ERR server cannot register event for this connection` | 只打日志 |
| 请求缓冲扩容失败 | 同上 | `-ERR out of memory (query buffer grow failed)` | 只打日志 |
| 输出缓冲超 `MAX_OUTBUF` | —— | `-ERR output buffer limit reached, closing` | （本轮新增） |

**fd 耗尽那条最特殊，值得单独讲**：`accept()` 因 `EMFILE` 失败时，
内核**根本没有返回 fd** —— 没有 fd 就没法 `write` 任何东西，连
「回一条错误再关」都做不到。客户端唯一的体验就是：连接建立了，
然后永远没有回应，直到它自己超时。

解法是**预留一个应急 fd**（Redis 同款）：

```mermaid
flowchart TD
    A["accept() 返回 EMFILE"] --> B["close(应急 fd)<br/>★ 立刻腾出 1 个名额"]
    B --> C["再 accept 一次<br/>这次能成功"]
    C --> D["回 -ERR out of file descriptors<br/>然后 close"]
    D --> E["重新 open /dev/null 占位<br/>为下一次做准备"]
    E --> F["break，本轮不再 accept"]
```

> ★ 代价是**永久占用 1 个 fd**：可用连接数比 `ulimit -n` 少 1。
> 这笔账很划算 —— 用 1 个 fd 换「爆掉的瞬间能说清原因」。
>
> ★ 消息里区分 **EMFILE**（本进程配额满）和 **ENFILE**（整机 fd 满）：
> 两者的处置方式完全不同（调 `ulimit -n` vs 查别的进程），
> 不给区别就等于让运维从头猜。

**实测**（把服务器 `ulimit -n` 压到 40）：

```
[init] 已预留应急 fd=4（fd 耗尽时用它回 -ERR）
[listen] fd 耗尽（EMFILE），用应急 fd 回 -ERR 后继续
第 35 条连接收到: -ERR out of file descriptors (EMFILE)
```

> **教训：错误路径的「可诊断性」和功能本身一样重要。**
> 一个只会 `close()` 的服务器，出问题时所有人的第一反应都是
> 「网络有问题吧」—— 而真相可能只是它自己满了。

#### 教训五：修 bug 之前，先证明 bug 存在

同一次测试里我还"发现"了一个解析器缺陷：大包 + 流水线会误杀合法请求。
我写了 100 行存档逻辑改 `parser.c`（给 `Client` 加 `bulk_buf`、让游标持续推进）。

改完之后用**原始 HEAD 构建**回头验证 —— 原代码在 **8/8 种合法切分场景**下
完全正确：值到齐+紧跟命令（任意切点）、1MB 大值分片、逐字节发送、
值分两次到、只差 CRLF …… **一个都没坏。**

那 100 行是凭空的，已全部 `git checkout` 回退。

> **教训：先构造一个在当前代码上必然失败的用例，再去改代码。**
> 「改完看起来好了」不能证明原来坏过 —— 很可能改的是别的东西。
> 这条和 `REVIEW` 里那次「假设回复是 7 字节」的错误是同一类：
> **先验证前提，再调试实现。**
